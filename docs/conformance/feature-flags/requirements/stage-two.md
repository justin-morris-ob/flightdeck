# Targeting, unified authoring and consumer observable requirements

The unified redesign supersedes earlier project-wide metadata, environment-selectable local inventory and per-flag segment pinning. [Unified verification](../../../stage-two-verification.md#unified-redesign-verification) records integrated local checks; requirements are acceptance criteria, not evidence by themselves. Stage 1 security/audit/concurrency and independent Atlas composition still apply. Typed POST evaluation replaces the preproduction GET/boolean API. Segment publication advances the environment catalog revision (attributes unchanged) to invalidate stale flag review; original audit snapshots remain verbatim with a separate `following_migrated` cutover event.

## §1 Typed publication and segment following

- **§1.1** Each environment configuration declares a boolean, string, number or JSON off value. Every fixed outcome and variant payload must have that same type. Invalid values, weights, references or oversized inputs fail before any revision/audit write.
- **§1.2** Rules have stable IDs and explicit array order. Each rule ANDs its conditions and referenced segment predicates. The first eligible rule selects the outcome; otherwise the configured default applies.
- **§1.3** Project catalogs define typed scalar/string-list attributes. Catalog mutations require the expected revision and append actor-attributed history atomically. Segments belong to an explicit project/environment and cannot reference another scope.
- **§1.4** Flag publication retains validated attribute definitions and attaches current-published segment references. Segment draft/catalog edits alone do not alter published decisions. Explicit segment publication advances all published local references atomically without per-flag republishing.
- **§1.5** Changing one environment's type/configuration does not mutate another environment. Existing flag IDs, enabled/archive state and revisions survive migration.

## §2 Evaluation and assignment

- **§2.1** Precedence is archived, environment disabled, active exact override, first eligible ordered rule, configured default. `enabled` denotes the master environment gate, independently of the returned typed value.
- **§2.2** Custom conditions use published types with no coercion. Missing/wrong-type attributes do not satisfy negative comparisons. Presence/absence is explicit; a wrong type satisfies neither. Built-in tenant/subject predicates read top-level context.
- **§2.3** Allocation follows the exact versioned byte/hash specification in [evaluation-spec.md](../../../evaluation-spec.md). Immutable namespaces and stable IDs determine buckets; display names do not. Raising a rollout threshold preserves existing eligibility for unchanged inputs.
- **§2.4** Zero rollout never admits; full rollout with a fixed value needs no subject. Partial rollout and every variant outcome require both tenant and stable subject. Missing identity is explained, not assigned randomly.
- **§2.5** Variant weights are integer basis points totaling 10000, using ordered half-open intervals and a separate hash purpose from admission. No automatic weight redistribution occurs. Reassignment-sensitive changes produce warnings and a same-context current/draft preview.
- **§2.6** Unknown flags are errors. Decisions include tagged value, scope/key, gate, reason, flag/catalog revisions, selected variant and matched rule/override IDs. Trace excludes raw subject/context values. Preview and consumer evaluation use the same evaluator; preview does not publish.
- **§2.7** Language-neutral permanent cases cover precedence, exact boundaries, missing/wrong-type conditions, negative operators, expiry, unknown/archive gates and hash encoding. Evaluations are not stored as exposure events or results.

## §3 Scope and overrides

- **§3.1** Service evaluation requires an authorized project/environment and a tenant in the credential's explicit grant before flag lookup. Credentials grant 1–20 tenants; migration restricts existing local credentials to `local-tenant`. Granting a tenant is not proof of BC membership.
- **§3.2** Overrides match exact flag/project/environment/tenant/subject, require owner/reason/future expiry, and select a typed value or fixed variant. They cannot override archive/disable. At the expiry instant they are expired. Revocation and audit are atomic; runtime cannot arbitrarily rewrite an override.
- **§3.3** Publishing must reject incompatibility with active overrides. Cross-organization/project/environment operations cannot read or mutate another scope. Viewers cannot write; editors cannot issue credentials.
- **§3.4** The backend client POSTs context, validates decision scope/key/tagged type and distinguishes a declared typed fallback from a service decision. Authorization failure throws, never silently falls back. Secrets stay out of browser bundles/storage.

## §4 Actual operator surface

- **§4.1** Shared standalone/Atlas pages provide structured typed values, catalog/segment editing, ordered rules, variants, scoped override create/revoke and audit. They use Onebrief components/tokens, not copied reference-product UI.
- **§4.2** Preview shows exact current/proposed decisions and assignment warnings; publication requires explicit scoped review/confirmation. Invalid JSON/weights cannot appear successfully published.
- **§4.3** Viewers have read-only authoring controls and can simulate published context. Embedded pages defer chrome/theme ownership to Atlas. Both themes render actual targeting/playground content without overlapping toolkit blocks.
- **§4.4** Inspecting published behavior, advanced controls or history must not silently discard unpublished flag edits or simulation context. Navigation that would discard edits requires explicit handling.
- **§4.5** Flag and segment creation use dedicated screens within the visible project and fixed local environment context, not modal forms. Cancel/Back returns to the inventory/library; leaving unsaved edits requires explicit discard. Saving remains guarded while in flight. Short confirmation/review dialogs do not replace the creation screens.
- **§4.6** Flag detail presents full-width Lifecycle, Published behavior and Audience blocks, followed by Test a context on its own full-width row at every viewport size. Edit audience expands the Audience block in place instead of opening a drawer. Change lifecycle, Change gate and audience/exception controls belong to their corresponding blocks. Moving/opening controls preserves draft/context state; synthetic-context testing remains an evaluation of published configuration. Viewer/master mutation restrictions remain intact, and metadata, advanced inspection and audit remain reachable.

## §5 Deployment-local inventory and master observation

- **§5.1** Immutable keys identify project flags; name, description, owner, lifecycle, archive state and flag revisions are local to an environment. Creation initializes Off only in the deployment's environment and does not provision other environments.
- **§5.2** The local environment comes from server deployment configuration, never a browser-selected environment or mode. Local inventory has gates/audience summaries and lifecycle filters, not an environment selector or comparison matrix.
- **§5.3** Flags, Segments and Audit trail are peer views with explicit project context; settings is secondary. Standalone/Atlas integration preserves toolkit and shell ownership.
- **§5.4** Master compares actually reported per-environment lifecycle, gates, typed behavior and audiences; drill-down is read-only. Missing state is Unavailable, never Off. Master cannot create/edit/publish/toggle, mutate settings or send remote change requests. Configured dashboard links do not grant local authorization.
- **§5.5** Operator inventory remains bounded to 20 flags/page with stable cursors/search/archive filters and scoped environment summaries. Service credentials cannot read management inventory; inaccessible scopes and malformed inputs are rejected. Every mutation, including project-only routes, enforces configured local scope and rejects master mode.
- **§5.6** Lifecycle is Development, Release, System or Permissions. Explicit local metadata review/save does not change gates, values, audiences or other environments. No automatic lifecycle transition, expiration or cleanup is inferred.
- **§5.7** Creation retains Name, Flag key, Owner and Description. Large native radio cards group Development/Release as temporary delivery and System/Permissions as long-lived purposes; keyboard selection and visible focus remain available. Before a key is manually edited, Name changes generate lowercase underscore-separated keys within the existing letter-first/100-character contract. Manual keys are not overwritten by later Name changes; existing flags' keys never change when editing metadata.
- **§5.8** Lifecycle-grouped local inventory renders full-width table headings for the groups present on the current page, expanded by default. Each heading is a keyboard-focusable disclosure button with `aria-expanded` and associations to its controlled rows. Click, Enter or Space toggles only that group's flag rows; the heading, other group states and focus remain intact. Selecting or reselecting a particular lifecycle filter expands that group automatically while preserving the other groups' collapse choices. Each lifecycle uses its own table row group, without inheriting create-form card layout. Collapse is inventory-local presentation state and does not mutate flags or change the bounded page/filter contract. Ungrouped inventory shows all returned rows; master remains an ungrouped read-only comparison. Create-form lifecycle cards retain their separate layout.

## §6 Simple audience authoring with preserved advanced capabilities

- **§6.1** Compatible Boolean flags expose Everyone or Selected audiences. Everyone is explicit; an empty Selected audience matches nobody through audience rules and never implicitly becomes Everyone.
- **§6.2** Each selected Flightdeck segment is an OR alternative, implemented as one full-rollout true rule with false off/default values. Within each segment ANY block matches and ALL conditions inside a block match. Environment gates, archive state and active individual-override precedence remain unchanged.
- **§6.3** Simple edits preserve allocation namespace/hash version and retained rule IDs/names. Arbitrary conditions, partial rollouts, variants, typed outcomes, duplicate branches or other non-representable configurations are not automatically rewritten or converted.
- **§6.4** Working advanced authoring and simulation stay mounted in their own full-width, closed-by-default Advanced controls disclosure below Audience and Test a context, never inside the audience editor. Both surfaces share one draft; edits, undo, raw-field validation and test contexts survive disclosure/editor transitions. Hidden invalid native configuration fields invalidate review and surface an error outside the disclosure; they cannot publish silently. Discard intentionally resets draft fields without clearing the published-context input.
- **§6.5** The audience editor places Discard draft changes on the left and Review changes on the right. Review uses the existing server validation/preview route and opens one Targeting change review modal with current/proposed audience, exact configuration, explicit local scope, unchanged gate/lifecycle and allocation warnings. Empty-context validation is not a BC-user simulation or membership-size estimate. Cancel retains the draft and performs no write; only explicit Publish applies the reviewed snapshot with flag/catalog revision guards. Unchanged authored input is identified without hiding that publishing still records a new revision/catalog refresh. Viewers cannot author or publish.
- **§6.6** People/email, organization and group lookup uses the same compact, always-visible multi-select search presentation in flag editing and Create segment, with grouped/filterable results and persistent selection chips. Flag lookup searches its configured directory after a short debounce and at least two characters; it does not require reveal/submit/Done steps. Clearing/changing a query preserves selected IDs and invalidates late results. Connections remain private and scoped; disconnected/error states are explicit, never replaced with demo results. Only editor/admin can search/resolve; viewers read status only. No membership replica or evaluation-time directory call is introduced.
- **§6.7** Metadata/version, advanced empty-context diagnostics and lifecycle actions do not obscure default audience controls. Advanced functionality is not labeled under development; connection absence and lookup failures are distinguished.
- **§6.8** Direct people/organization/group branches OR with selected segments and compile to ordinary actual-tenant/source equality guards plus people `in` or membership `contains_any`. People IDs are canonical lowercase UUIDs; organization/group IDs are canonical positive int32 decimal strings; BC tenant GUIDs normalize to lowercase. Nonrepresentable advanced configurations are preserved rather than converted.
- **§6.9** Tenant/subject/source and effective organization/group membership fields have built-in types; directory selection requires no manual catalog preparation. Incompatible declared types are rejected. Custom traits use the environment-local catalog. Segment branches retain tenant/source guards; effective memberships apply across organizations. Trait blocks support exact `ends_with` string matching; missing/wrong-type traits do not match.
- **§6.10** Private `FLIGHTDECK_BC_DIRECTORY_CONFIG` is a mode-0600 JSON file with at most 20 unique project/environment bindings. Invalid configured files fail startup. The separate supported BC API provisions/revokes dedicated directory credentials through tenant-admin authorization, with a one-time secret and purpose `flightdeck-directory` / scope `flightdeck-directory:read`; it is not a released capability or production onboarding guarantee.
- **§6.11** The separate BC consumer uses fresh actual-tenant admission metadata, not browser projection. Unassigned/foreign tenants retain legacy BC evaluation without a Flightdeck request. Directory outages must not alter evaluation of existing saved predicates against trusted consumer context.
- **§6.12** Temporary POC segment authoring exposes synthetic people, organizations and groups directly through the visible membership search, with three fixtures of each kind and no opt-in click. Fixtures are marked as synthetic in code, but the picker has no directory-source switch, demo banner or demo labels in chips/tooltips/accessibility text. Searches filter the fixtures locally, never replacing live directory failures. Results are bounded visually and clearing search preserves selected cards. Saved fixture selections retain a separate synthetic source/tenant and their names after reload, without a BC resolve call. Viewer/master authoring restrictions and separate segment draft/publication remain unchanged; flag audience editing still uses live lookup.
- **§6.13** Segment creation shows distinct bordered numbered People & memberships and Trait rules blocks with an OR divider and ANY-block heading. Trait rules are optional and initially visible without silently adding a condition to the saved definition. Conditions within a trait block match ALL; adding/removing conditions or OR blocks preserves unrelated membership selections. Name/Description share a row at desktop widths and stack on narrow screens; the immutable key remains available.
- **§6.14** Selected people, organizations and groups show distinct type icons and text labels with total/per-kind counts. The collapsed preview renders at most six chips without losing hidden selections. View all opens a bounded scrollable list with local filtering by label/email/type/ID; removal and undo affect the correct target even when filtered. Read-only inspection can expand/filter but cannot remove. Full names and missing-label/source markers remain accessible.
- **§6.15** Segment selection batches memberships into existing 20-ID tenant/source-guarded blocks and permits multiple batches per kind within the shared 20-block limit, including trait blocks. Capacity checks prevent adding a target that would require a 21st block, without blocking removal or additions that fit an existing batch. No API/evaluator operand limit or direct flag-authoring limit is expanded.
- **§6.16** Flag audience editing uses one search for People, Organizations, Groups and published Flightdeck Segments, with All/type filters, grouped typed results and one selected-chip list with combined/per-kind counts, removal and undo. Segment names/keys filter the authorized environment catalog locally; draft-only segments are not selectable. Segment search/selection stays usable when the directory is disconnected, loading or failing, while directory state/errors remain explicit and never replaced by fixtures. Search changes and directory replies preserve both selection types. Removing a selection then changing another selection invalidates the old undo. Segment selections follow current publication, and the existing 20-branch/20-ID-per-directory-kind limits, OR semantics and explicit flag review/publication remain unchanged. Segment definition authoring does not gain nested segments.

## §7 Consumer context, OpenFeature and reusable lab

- **§7.1** String-list attributes contain at most 100 strings of at most 500 characters each. Exact `contains_any` / `contains_all` use 1–20 string operands; missing/wrong-type lists never match, empty lists are present, and no scalar/string coercion occurs. Invalid operator/type pairs fail publication. Catalog editing and the advanced JSON-array playground use the same semantics.
- **§7.2** Serialized UTF-8 evaluation context is bounded to 32 KiB and 32 custom attributes. The 64-KiB HTTP envelope accommodates a maximum context and separately bounded proposed configuration. A maximum-sized context can be evaluated through the actual HTTP/provider/SDK boundary and previewed; an over-bound context fails instead of truncating.
- **§7.3** The independent server provider maps OpenFeature targetingKey to subjectId, tenantId to its top-level field and supported custom values to attributes. It fixes service credential/project/environment outside evaluation context, rejects unsupported/ambiguous context, validates response scope/key/type/revisions, prohibits redirects and bounds response consumption with one finite deadline.
- **§7.4** Actual typed SDK detail calls distinguish service decisions from caller defaults. `enforceFlightdeckPolicy` rejects authorization and nonretryable context/request errors even though the SDK normally returns defaults on errors. Recoverable errors retain explicit error/source metadata and the caller-selected default; no directory call, retry, cache or exposure is implied.
- **§7.5** The loopback-only consumer lab refuses production startup and accepts only known persona/capability/scenario IDs, never arbitrary browser context or credentials. Its backend owns the synthetic subject/source/tenant/membership mapping. Setup preserves existing configuration and stores its dedicated scoped credential privately. A selection change clears the old browser decision.
- **§7.6** The lab consumes real persisted Boolean/string/number/object decisions through the provider. Simulated unavailable/malformed transports are labeled as such; wrong-tenant/invalid-credential scenarios call Flightdeck and surface an explicit authorization error. It demonstrates context evaluation, not real BC identity or an authoring directory.
- **§7.7** Flightdeck owns committed, assertion-backed Playwright recording scenarios and presentation helpers without BC source/runtime/session dependencies. Recording starts/reuses the local services, preserves managed configuration, and exports captioned MP4s only for successful scenarios. Export failure fails the command and removes incomplete/stale selected-scenario exports. Generated recordings and private credentials remain ignored; recorder-owned services stop after the run while reused services remain available.

## §8 Segment draft, publication, history and audit

- **§8.1** Creating/saving a segment produces an explicitly non-live draft. Published definition summaries remain independent of draft additions. Usage lists actual published references only; unsaved browser-only flag drafts are not invented as persisted usage or impact.
- **§8.2** Segment publication requires scoped before/after review and optimistic guards binding both draft and affected published-reference set. Concurrent attachment/detachment or relevant flag change invalidates stale review. Publication updates all local published references atomically, including Off flags, but does not change flag revisions, gates, direct selections or unrelated drafts.
- **§8.3** Publication clears the draft and retains immutable published history. Historical versions are inspectable, not per-flag selectable pins. Explicit guarded restore replaces the unpublished draft after confirmation; it never directly changes published behavior. Restored contents require separate review/publication.
- **§8.4** Unified Audit trail supports scoped bounded search/filter/pagination and immutable actor/time/action/before/after details. Segment publication records the exact affected published references atomically. Earlier events preserve event-time truth; migrated historical pins are not relabeled as following.
- **§8.5** Audit inspection cannot edit, restore or republish. Audit is configuration history, not SDK propagation, evaluation telemetry, exposure, population estimates or production-deployment proof.
- **§8.6** Segment records expose only the latest 20 retained definitions plus a history cursor; the scoped history endpoint and **Load older** make all retained versions inspectable without an unbounded response. Audit state preserves event-time published/draft/usage snapshots but omits accumulated history/page fields; separate segment-history retention remains intact.
- **§8.7** Existing segment detail groups identity/key, inspected version, concise selected-target/trait contents and publication boundary in one overview card. Identity and summary come from the explicitly inspected definition, not unpublished metadata presented as published. Definition/Where used/Version history are linked content tabs with selected state, roving focus and Arrow/Home/End navigation; only the selected panel is visible. Definition renders full-width membership and trait sections, consolidating guarded membership batches without dropping IDs or changing matching logic. The reference table belongs to Where used. Historical inspection is labeled not active and leaving history returns to current publication (or a saved draft when no publication exists). Published/draft separation, viewer restrictions, history paging and explicit restore/publication guards remain intact.
- **§8.8** The full audit row opens its recorded event through a whole-row pointer target and a native keyboard-operable event button. While selected, results become a compact scrollable event list showing abbreviated UTC date/time, action and the recorded flag/segment name, with a single current-event marker. Full timestamp/year remains available in accessible labels, date tooltips and event detail. Selecting another event updates immutable detail without restoring the full table. Close restores the same full results, filters and page and returns focus to the selected event control; applied filters, paging and refresh clear the old selection. Desktop detail sits beside a narrow list; narrow screens stack the bounded list above detail. Actor, scope, identity, exact snapshots and recorded affected-reference information remain available without editing or rewriting history.
- **§8.9** Selected audit detail groups summary/actor/time/scope/identities, recorded before/after changes, recorded affected references and the historical-snapshot notice/object handoff into distinct bordered, padded containers with consistent spacing. Raw snapshot disclosure stays with the before/after comparison. The impact container appears only when the event records an affected-reference field, including its explicit empty-set state. All recorded values, reference gates/revisions and read-only boundaries remain unchanged; summary focus, compact navigation and close/focus restoration are preserved. Cards and metadata reflow without horizontal document overflow on narrow screens.
